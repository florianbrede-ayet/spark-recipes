# Benchmark provenance — 2026-08-23

**Source:** live quick benchmark of the unchanged GMU 0.87 profile, 2026-08-23.
**Subject:** exactly the deployment described in this bundle — GMU 0.87,
maxseq 6, threshold 1024, batched 4096, retention 4096, DSpark k5, graph-estimate
flag 0, API ceiling 1,048,576, recipe SHA `2dcd8e9a…98379b`.
**Nothing was restarted, reconfigured, cache-cleared or rolled back** to obtain
these numbers.

> Read the definitions before the tables. Every one of these figures is a
> *service rate under a specific cache state*, and the aggregate and per-stream
> columns are not interchangeable.

---

## 1. What these numbers are — and are not

**Aggregate (whole-batch) tok/s.** Exact API output tokens (`128 × c`) divided
by the wall-clock time from releasing all `c` clients simultaneously until the
last non-streaming response completed. **TTFT is included.** This is a
whole-batch service rate.

**Per-stream tok/s.** `128 ÷ that individual request's wall time`. The pooled
range across a cell's requests is reported.

These deliberately are **not** token-event-only decode-window ceilings. A
decode-window measurement that excludes prefill and queueing would produce
higher numbers that describe a different thing.

**Cold vs warm.** Rows marked `d0` start from an empty cache for that prompt.
Rows marked *prewarmed* were prefilled **outside the reported timing** and then
measured. A warm row is a **warm-cache service measurement, not a cold prefill
measurement.**

## 2. TG128 — generation of 128 tokens

Three measured batches per cell. All 66 TG requests returned exact API usage of
128 tokens; no BOS marker, empty output, request error or preemption occurred.

| Depth / cache state | c | Aggregate tok/s (mean ± sample SD) | Range | Per-stream tok/s (pooled range) |
|---|---:|---:|---:|---:|
| d0 (cold) | 1 | **40.25 ± 18.28** | 26.85–61.07 | 26.85–61.08 |
| d0 (cold) | 4 | **60.86 ± 3.75** | 56.60–63.70 | 14.15–39.78 |
| d0 (cold) | 6 | **79.91 ± 3.33** | 77.00–83.54 | 12.83–31.97 |
| d50K, prewarmed (warm) | 1 | **31.79 ± 1.22** | 30.58–33.02 | 30.62–33.06 |
| d50K, prewarmed (warm) | 4 | **65.77 ± 1.56** | 64.52–67.51 | 16.14–31.38 |
| d50K, prewarmed (warm) | 6 | **89.02 ± 4.83** | 83.85–93.40 | 13.98–26.74 |

How to read this:

* **Aggregate rises with concurrency; per-stream falls.** At `c=6`, warm, the
  cluster delivers ~89 tok/s in total while any individual stream sees
  ~14–27 tok/s. Both are true. Quoting the aggregate as a per-user speed is
  wrong.
* **The `d0, c=1` spread is large** (SD 18.28 on a mean of 40.25, range
  26.85–61.07). A single cold request's rate is dominated by TTFT and DSpark
  acceptance variance. Do not treat 40.25 as a stable single-stream figure.
* **Depth costs single-stream rate but helps aggregate.** At `c=1`, warm 50K is
  *slower* than cold `d0` (31.79 vs 40.25) — longer context, more attention work
  per token. At `c=6` the warm case is *faster* in aggregate (89.02 vs 79.91),
  because cache hits remove prefill work that would otherwise compete.

### The d50K cache state, exactly

Six deterministic prefixes, distinct from token zero, were prefilled once
outside the reported timing and then independently probed. Every prefix had
exactly **49,920 / 50,000** cached tokens — the complete 256-token blocks; the
80-token remainder does not form a block. The measured `c1`/`c4`/`c6` batches
then showed exact cache-hit deltas of **49,920 / 199,680 / 299,520** tokens.

## 3. PP4096 — prompt processing

PP rate is the requested incremental tokens (4,096) divided by the server's
`request_prefill_time_seconds` delta. Each repetition used a distinct 4K tail so
the benchmark could not hit its own cache.

| Case | Incremental prompt tok/s (mean ± sample SD) | Range | Server evidence per repetition |
|---|---:|---:|---|
| d0 (cold) | **1,917.95 ± 6.94** | 1,911.27–1,925.12 | 4,096 computed, 0 cached |
| prewarmed d100K + incremental 4,096 (warm) | **1,403.00 ± 5.33** | 1,398.95–1,409.05 | 99,840 cached, 4,256 computed |

The warm row is **incremental cached-prefix PP, not cold 104K PP.** The API
prompt contained 104,096 tokens, of which 99,840 were cache hits. The server
recomputed the uncached 160-token boundary of the 100K prefix plus the requested
4,096-token extension — hence **4,256 physical compute tokens** for a 4,096-token
increment. The rate is lower than cold `d0` because attention over a 100K
context costs more per new token, not because caching hurt.

**Excluded data, disclosed:** the first PP pass reused identical full prompts on
repetitions 2–3 and therefore hit its own cache. Those contaminated rows remain
in the source `summary.json` for audit and are excluded from the table above.
The reported PP results come from `pp-rerun-summary.json` with distinct tails.

## 4. Validity controls

* **Idle gate.** 30.43 s with running/waiting at 0/0 and zero movement in the
  prompt, generation, success and preemption counters before starting.
* **No overlapping traffic.** Per-case counter deltas matched the exact request
  and token counts for every accepted case.
* **DSpark active throughout.** Benchmark-window delta from the pre-task
  snapshot: **+14,940 drafted / +5,538 accepted = 37.1 % token acceptance.**
* **Zero preemptions,** cumulative.
* Final API and dashboard HTTP 200; both rank containers unchanged and up; both
  RoCE HCAs ACTIVE; GPUs idle at 54/55 °C; memory PSI avg10/60/300 = 0.
* No Xid, OOM kill, fatal CUDA/NCCL/B12X/EngineCore error, rank loss or matching
  container traceback. Generic `_memdescAllocInternal` NVRM warnings occurred,
  were recorded, and were not treated as a veto per operator direction.
* No restart, config change, cache clear, service change or rollback was
  performed for the benchmark.

Source evidence (not vendored here): `summary.json`, `pp-rerun-summary.json`,
`raw/`, `method.json`, `prompt-manifest.json`, `preflight/`, `health/`.

## 5. Quoting these numbers

Fair:

> *"On 2026-08-23, this two-node GB10 TP2 deployment served ~89 aggregate tok/s
> for six concurrent 128-token generations over a warm 50K-token prefix
> (per-stream ~14–27 tok/s), and ingested ~1,918 tok/s of cold prompt at 4K."*

Not supported by this evidence:

* ~~"~89 tokens per second per user."~~ That is the whole-batch aggregate.
* ~~"1,403 tok/s for 104K prompts."~~ That is a 4,096-token increment on a
  99,840-token cache hit.
* ~~"40 tok/s single-stream."~~ The `c=1` cold cell ranged 26.85–61.07.
* Any comparison to a run with a different profile, image, model revision or
  cache state. Re-benchmark instead.
